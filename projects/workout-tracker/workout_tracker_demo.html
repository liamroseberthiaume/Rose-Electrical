Workout Tracker API

A REST backend for planning, scheduling and reviewing training sessions — JWT authentication with refresh-token rotation, a normalised exercise catalogue, and progress reports aggregated in SQL. Everything below is the real interface, running against an in-browser stand-in for the Python server.

FastAPI SQLAlchemy 2.0 Alembic JWT + bcrypt SQLite → Postgres 50 assertions passing
Try it Read the write-up

This is a sandbox. The real project is a Python service with a database behind it, which a static site can’t host. So the frontend below talks to a stand-in that reimplements the same endpoints in your browser — identical request shapes, status codes and report maths, backed by memory instead of SQL. Nothing is sent anywhere, and a reload resets it. It ships pre-loaded with eight weeks of training so the reports have something to say.

Under the hood

What the real service does

Auth that actually invalidates

A 15-minute access token plus a single-use refresh token. Refreshing rotates the pair; replaying a spent token means it leaked, so every session for that user is revoked. Logout adds the access token’s jti to a denylist so it dies immediately rather than lingering.

Ownership by construction

Every query filters on user_id. Another user’s workout returns 404, not 403 — a 403 would confirm the row exists and leak that someone owns it.

Normalised, not JSON blobs

The prescription lives on a join row; the exercise catalogue is shared and immutable. That is what lets reports run GROUP BY muscle_group in SQL instead of parsing JSON in Python.

Timestamps that survive SQLite

SQLite drops timezone info, so a custom UTCDateTime type coerces to UTC on write and re-attaches it on read. Without it, a session booked for 18:00 renders three hours off.
